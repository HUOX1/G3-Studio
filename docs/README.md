## 协作模式

**代码由 AI 编写，用户负责设计与验收。** 用户不懂代码，通过 Krita 画设计稿、实机截图反馈，指导开发方向；AI 负责具体实现、调试、文档。

所有技术决策以"用户视觉验收通过"为准。

### 日志更新输出约定

更新 `history.md` / `feature-status.md` / `architecture.md` 时，用户可直接复制以下要求贴在对话最前面：

```
【输出要求】
1. 短文件（如 README.md）整份给出；长文件（如 history.md、architecture.md、
   feature-status.md）只给「新增章节 / 要替换的段落」，用户自己粘贴过去。
   长文件不要整份重发。
2. 只输出文件内容，放在一个 md 代码块里，不要有任何代码块之外的文字。
3. 不要"我做了什么""还差什么""说明"这类总结或解释。
4. 表格必须用 Markdown 表格，不要用列表代替。
5. 如果更新多个文件，每个文件一个独立代码块，代码块前一行标明文件名
   （如：文件：history.md）。
6. 文件内容从第一行到最后一行完整给出，不要用"..."跳过。
7. 若文件内部已含 ``` 代码块，外层请改用 ```` （四个反引号）包裹，
   避免嵌套冲突。
8. 如果用户明确说"一整个代码块方便复制"，就把所有文件的更新放进一个
   ```` 代码块里，用「===== 文件：xxx =====」分隔。
```

**为什么定这个约定**：
- 日志长度常接近上下文上限。若 AI 在代码块外附带解释、总结或列表格式，容易挤掉真正的日志内容，导致更新中断或格式粘贴后错乱。把要求前置，可保证一次输出即可直接存盘。
- 长文件整份重发会占用大量上下文，且用户已有本地版本，只需提供必要的增量修改段落。
- 内层已有 ``` 时外层用 ````，避免 Markdown 嵌套渲染破坏。

## 更新日志收录原则（2026-10-23 起）

- **记录**：新功能、功能性重构、字体系统的功能和排版体系更新、补丁注入器的能力升级、重要设计决策，以及对应修改的源码文件路径。
- **不单独记录**：小 Bug 修复、微小图标/间距调整、临时排障过程及补丁格式修正等；必要时只在功能状态中描述最终效果。
- **验收状态**：区分源码已修改、用户确认生效与仍待验证；不根据历史补丁文件推断实装成功。
- **文件记录格式**：写明「改动内容」和「修改文件（项目相对路径）」，不记录补丁文件名、下载链接或补丁版本号。
