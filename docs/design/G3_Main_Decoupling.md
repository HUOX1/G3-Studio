# G3 `main.gd` 解耦档案

> **档案更新日期：2026-10-23**
> **当前状态：UI-S8l 已由用户确认通过；本次只更新文档，不修改业务源码。**
> **用途：这是 `main.gd` 解耦工作的唯一持续维护、可供后续接手的详细档案。**

## 0. 最终结论与维护规则

本轮的核心目标已经达到：把 `g3_frontend/scripts/main.gd` 从承载大量业务请求和业务数据处理的单体脚本，收敛为负责应用组合、全局 UI 状态和跨模块协调的入口。当前不建议为了进一步降低行数而继续大规模拆分，也不应仅因为还有较长函数或较多变量就自动新建脚本。

- 最初记录的 `main.gd`：**4,620 行**。
- S8l 已验收源码副本：**2,705 行**。
- 直接净减少：**1,915 行，约 41.45%**。
- 主要后端请求入口已经迁入控制器/路由层；当前静态扫描未发现 `backend.request(...)`、`_backend_router.request(...)` 直接调用。
- 原先发现的 `main.gd` 对 `game_section._batch_mode` 的跨模块私有字段访问，已改为 `game_section.is_batch_mode()`。
- S8l 清理了确认没有读取用途的遗留变量/赋值，并把完整契约从 1,765 项扩展到 **1,769 项**。用户已确认完整回归通过：**50 个场景、1,769 项检查**。
- 本轮后续应进入稳定维护。只有出现具体功能需求、可复现缺陷或明确的职责泄漏时才开启新一轮重构；不要为了减少数字而持续拆分。

## 1. 原始目标、边界与验收原则

### 1.1 原始目标

用户希望减少 `main.gd` 的体量和职责负担，降低修改一个业务功能时牵连其他区域的风险。目标不只是“行数变少”，还包括：

1. 请求发起、请求身份、异步响应和断线失效归属明确；
2. 游戏、电影、设置、扫描导入、封面工具和模拟器等业务各自有明确的控制器/构建器；
3. 业务状态由真正拥有它的模块管理；
4. `main.gd` 不再直接读写其他模块的私有实现细节；
5. UI 组装、全局板块切换和跨视图协调仍留在应用入口，不为追求行数把它们盲目迁走；
6. 每个增量补丁都能由项目现有 PowerShell 注入器安全应用，并由完整契约和必要的手动操作验收。

### 1.2 `main.gd` 应保留的职责

当前应保留在 `main.gd` 的内容包括：

- `_ready()` 及应用启动阶段的顺序协调；
- `_build_3d_world()`、`_build_ui()`、`_build_backend()` 等组合根工作：创建节点/视图/控制器、接收 Builder 产物、注入依赖、连接信号；
- `_set_section()`、`_transition_to_section()`、`_apply_section_now()` 等跨板块切换、可见性、动画与全局主题协调；
- `_on_backend_event()` 等需要协调多个业务模块和渲染所有权的全局事件；
- 将控制器结果映射到弹窗、文件选择器、错误提示、刷新和可见性变化的 UI 适配工作；
- 由多个视图共享的应用级状态与生命周期。

这些职责可能仍然较长，但它们有合理的应用根归属。不能仅因函数行数较多，就把整段 `_build_ui()`、`_build_backend()` 或全局事件协调迁入另一个巨型脚本。

### 1.3 增量修改与验收规则

- 每次开始前核对当前源码基线、`docs/` 中的解耦档案、执行说明和相关补丁。
- 以用户本机实际源码和最新验收结果为最终事实；当前工作副本或历史补丁不自动代表用户磁盘状态。
- 先检查补丁文件头、路径、上下文和空白，再通过注入器暂存验证；不强制应用不匹配的补丁。
- 注入器失败且明确报告项目文件未改变时，不做回滚、重置或清理操作；应基于当前源版本重建补丁。
- 不使用 `git reset`、`checkout`、`clean`、`stash` 或强制覆盖来“修复”补丁失败。
- 每轮完成后，运行项目根目录的完整契约脚本；契约全绿后再按风险检查关键 UI 行为。
- 契约中的源码形状/硬编码计数断言必须和实际 `_check()` 数量、Runner marker 同步；不能把计数断言失败误判成业务功能失败。
- 只有用户确认通过后，才将该阶段视为已验收基线。

## 3. Stage 0～8.0：请求、生命周期和异步安全基础

### Stage 0：现状与边界审计

最初的 `main.gd` 约 4,620 行，跨越 UI 构建、后端请求、游戏/电影业务、设置、扫描、渲染生命周期等多个领域。早期统计记录约 154 个函数、约 127 个直接后端请求入口，以及一个非常庞大的 `_on_backend_response()`。

结论不是把所有代码集中搬进一个“Manager”，而是按业务归属迁移：控制器负责业务请求与响应状态，构建器负责可独立创建的视图片段，`main.gd` 保留应用组合和跨视图协调。

### Stage 1：BackendRouter 与基础请求

建立请求 ID 和 latest-slot 响应路由，处理新请求替换旧请求、重复响应、过期响应、发送失败和断线清理。逐步迁移主题、字体、设置、模拟器、游戏创建等请求入口，降低主文件对协议层的直接依赖。

### Stage 2：扫描与导入

将扫描/导入请求、结果路由和导入队列职责迁入 `library_scan_controller.gd`。覆盖模拟器及 Steam、GOG、Epic、Uplay、Rockstar、PSN 等平台，并尽量保留平台原有并发、跳过、计数和错误语义。后续 UI 阶段继续把扫描提示、payload 组装和数据转换迁出主文件。

### Stage 3：电影请求与播放

电影列表、元数据、创建/删除、封面和背景资源、TMDB、海报素材及播放相关请求逐步归入 `movie_controller.gd`。异步结果使用请求身份和生命周期规则，避免重复、过期或断线后的响应污染当前 UI。

### Stage 4：游戏业务请求

游戏列表、资料读写、CRUD、启动、游玩时长、Steam 手动/批量刮削、SGDB 和批量删除等请求归入 `game_controller.gd`。Steam 顺序批量刮削后来又被单独抽取成协调器，确保当前目标 ID、代次、取消、发送失败和旧回调处理集中管理。

### Stage 5：系统、封面工具和模拟器

系统设置请求、封面工具任务及进度、模拟器配置读取/写入等职责分别迁入 `system_settings_controller.gd`、`cover_tool_controller.gd`、`emulator_controller.gd`。完成后，`main.gd` 的直接后端请求发起已清零，但仍保留 UI 回调、弹窗和结果展示。

### Stage 6：渲染所有权与连接生命周期

引入 `render_ownership_coordinator.gd`，协调游戏和电影播放会话的渲染暂停/恢复、退出顺序、会话身份和延迟任务。增加会话关联、退出墓碑、延迟定时器失效和后端连接 epoch 隔离，防止旧会话或旧连接事件影响新状态。

### Stage 7.0～7.3：Steam 批量刮削

- **7.0 职责审计：** 确认 `main.gd` 仍应承担 UI/应用组装，不应为了行数搬走全部跨板块协调；识别 Steam 批量刮削状态机为合适迁移对象。
- **7.1 协调器：** 独立顺序队列、代次、当前游戏 ID、搜索/应用状态，覆盖无结果、无效返回、发送失败、取消、重启、过期和重复回调。
- **7.2 主程序接入：** `main.gd` 保留 UI 文案、控制器请求和刷新动作；断线取消任务，发送失败推进下一项。
- **7.3 异常回调加固：** 把当前游戏身份纳入 apply 结果关联，防止同代次旧游戏回调错误推进下一项。

该阶段的历史回归曾发生过 marker 数量与断言计数不一致；已通过只修复计数/契约的增量补丁解决，用户确认该阶段通过。

### Stage 8.0：Python 测试基线（独立）

这是 Python 后端历史测试兼容任务，不属于 `main.gd` 瘦身的组成部分。此前指定测试暴露过 `websockets` 依赖缺失和 Windows 路径分隔符断言问题，用户后来反馈相应修复通过。但历史全量 `python -m pytest -q` 收集问题未作为本轮解耦验收范围；不得把 Godot 契约通过等同于 Python 全量测试通过。

| 阶段 | 整合方向 | 结果 |

## 11. 重要修复记录与踩坑

1. **BOM：** UI-S3、UI-S4b 的初版补丁因文件首行 BOM 处理不当未能注入；修正版保留原编码标记后通过。
2. **尾随 Tab/空白：** UI-S5a、S8g、S8j 的初版补丁曾触碰原文件中带行尾空白的旧代码，注入器拒绝写入且明确报告项目文件未改变。处理原则是基于当前源码缩小/重建补丁，不绕过空白检查。
3. **契约 marker 与检查数：** Stage 7、S8c、S8e、S8j 曾出现检查行为通过但最终计数断言或源码形状断言失败。最终均通过最小契约修复解决，并由用户再次运行确认；以后修改测试时必须同时核对 `_check()` 计数、最终 `checks == N` 和 Runner marker。
4. **解析错误：** S6g 的电影信息 Builder 初版存在 GDScript 解析问题，独立修复后才继续；新脚本必须在契约前先经过 Godot 解析验证。
5. **重复声明/模块合并：** M6 发现过重复常量/路由定义风险；整合模块时要检查顶层声明重复、`preload` 路径和公开接口。
6. **禁止强制重置：** 注入失败不是重置项目的理由。只要注入器说项目文件未改变，就保留现状并重建补丁；不做 `reset/checkout/clean/stash`。
7. **避免微型脚本：** 用户明确指出每几行就新建一个 `.gd` 不妥。后续优先复用已有控制器/Builder/Presenter；只有职责边界清晰且有独立生命周期/测试价值时才考虑新文件。
8. **行数不是质量指标本身：** R1～R5 主要优化外围模块内部结构，`main.gd` 没有因此减少行数。后续应把“主文件职责减少”和“外围模块内部重构”分开记录，不能混为一谈。
