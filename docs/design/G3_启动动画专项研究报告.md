# G3 启动动画专项研究报告

- 研究日期：2026-10-29
- 引擎：`4.7.2.stable.official.ed1daf0bf`
- 性质：**只读研究**。未修改任何源码、未运行测试、未启动程序。
- 前提：启动架构已回归官方基线，窗口自首帧起即为 1244×700（无小窗、无 resize）。

---

## 0. 结论摘要

**推荐方案二：主场景内一次性遮幕淡出（CanvasLayer + Tween），并把遮幕颜色与 `boot_splash/bg_color` 绑成同一个常量。**

理由三条，都可以从代码直接验证：

1. **方案一（仅统一颜色）在 G3 上不成立**：三个分区各有独立色板，且启动分区由用户设置决定（`_read_local_start_section()`，默认 `games`）。没有任何单一 splash 颜色能同时匹配 GAMES 的冷灰蓝、MOVIES 的暖棕黑、SYSTEM 的亮蓝。
2. **方案三（氛围光渐亮 + UI 分层显现）代价与风险不成比例**：要分别改三套背景实现（ColorRect 着色器 / 3D cinema_ambient / 3D game_ambient）、还要逐控件调 modulate，且会与已有的封面入场动画、主题过渡互相争抢状态；漏恢复任何一个 uniform 就会永久变暗。
3. **方案二与分区无关、零启动开销、完全可撤销**：遮幕是纯 2D 全屏矩形，只在首帧后存在 0.45 秒，删掉 3 处代码即回到现状。

配套动作（方案一的核心动作，零风险）：把 `boot_splash/bg_color` 与遮幕颜色统一为 **GAMES 背景底色 `Color(0.055, 0.070, 0.095)`**，让"默认启动分区"的色相跳变降到最小。

## 1. 现状：启动时序与视觉构成

### 1.1 启动时序（代码顺序 + 上一轮实测）

| 阶段 | 时刻 | 屏幕上是什么 | 负责方 |
|---|---|---|---|
| 窗口上屏 | ≈3.2 s（实测） | Boot Splash 纯色 `#08111F` | 引擎 `RenderingServer` boot image |
| `_ready()` 构建 | 上屏后 ≈1 s（阻塞主线程） | 仍是 Boot Splash | — |
| 第 1 帧 | 构建结束当帧 | 完整 G3 界面（背景 + 侧栏 + 封面网格） | 主场景 |
| 第 1 帧之后 | — | 封面逐张入场（每张 1000 ms，间隔 180 ms） | `game_section.gd` |

关键事实：**`_ready()` 是单帧阻塞**，构建期间没有任何帧被 present，所以 Boot Splash 会一直停在屏幕上，直到第一帧整块替换它。这就是"割裂"的物理来源——不是渐变失败，而是**一次整帧替换**。

### 1.2 视觉责任划分

| 元素 | 实现 | 文件:行 | 基色（sRGB 8bit 近似） |
|---|---|---|---|
| Boot Splash 底色 | 项目设置 | `project.godot:17` | `#08111F`（8,17,31） |
| GAMES 分区背景 | `ColorRect` + `game_background.gdshader` | `game_section.gd:94,625` | bottom `#0E1218` → top `#1D2530`，叠加 glow `#618AC0` @0.075 |
| MOVIES 分区背景 | 3D `MeshInstance3D` + `cinema_ambient.gdshader` | `movie_wall.gd:11,168` | top `#241A0F` → bottom `#080505`，gold `#E0A85C` |
| SYSTEM 分区背景 | 3D `QuadMesh` + `game_ambient.gdshader` | `world_scene_builder.gd:71-79`，`main.gd:940-941` | top `#224278` → bottom `#0E2045`，含三条波 + 两层光点 + PS 图案 |
| 3D 世界骨架 | 相机 + WorldEnvironment + 三盏平行光 | `world_scene_builder.gd:17-69` | 环境光 0.08 能量、glow 分 6 级 |
| UI 根层 | `CanvasLayer(layer=10)` + 全屏 `Control` | `main.gd:442-450` | 主题色驱动 |
| 分区切换遮幕 | `CanvasLayer(layer=110)` + 全屏 `ColorRect` | `movie_bottom_overlay_builder.gd:60-73`，`main.gd:602,656` | `#050A0F`，alpha 0→1→0 |

**注意**：`game_ambient.gdshader` 的 `bg_top` / `bg_bottom` 在全部 GDScript 中**没有任何一处赋值**（全仓库搜索 0 命中），所以 SYSTEM 背景永远用 shader 默认色，不受主题影响。

### 1.3 割裂由三层差异叠加，不止颜色

| 层次 | Boot Splash | 正式界面 | 观感 |
|---|---|---|---|
| 色彩 | `#08111F` 偏蓝深色，纯平 | GAMES `#0E1218` 中性灰蓝 / MOVIES 暖棕 / SYSTEM 亮蓝 | 色相与明度同时跳 |
| 细节密度 | 0（纯色） | 侧栏 48 项 + 7 列封面 + 分隔线 + 光晕 | 从空到满，一次到位 |
| 运动 | 静止 | 封面逐张翻转入场、底部弹簧、呼吸光 | 静到动 |

**只改颜色只能消掉第一层**，第二层"细节突然出现"和第三层"运动突然启动"依然会造成"闪一下"的观感。这正是需要淡幕的原因。

## 2. Godot 4.7.2 官方支持的衔接方式

### 2.1 Boot Splash 的真实机制（源码证据）

```cpp
// main/main.cpp:3988  —— 在 setup2() 中只设置一次
RenderingServer::get_singleton()->set_boot_image_with_stretch(
        splash, boot_bg_color, RSE::SPLASH_STRETCH_MODE_DISABLED);
```

Boot Splash 不是场景、不是节点，而是 **RenderingServer 级别的一张 boot image**：设置一次，之后每帧由渲染服务器自己绘制，直到主场景请求第一帧真实画面为止。

由此得出三条硬约束：

| 事实 | 含义 |
|---|---|
| 没有"淡出 splash"的 API | 官方不支持让 splash 渐隐；切换必然是整帧替换 |
| 无法在 splash 上做事 | 它不属于场景树，`_ready` 里拿不到它 |
| 切换点 = 主场景首帧 | 想控制衔接，只能控制"首帧长什么样" |

### 2.2 可用的官方旋钮

| 旋钮 | 4.7.2 存在 | 语义 | 是否推荐 |
|---|---|---|---|
| `application/boot_splash/bg_color` | ✅ | splash 底色（`show_image=false` 时即全部内容） | **推荐**，用于与首帧对齐 |
| `application/boot_splash/image` + `stretch_mode` + `use_filter` | ✅ | 可放一张静态图（如 G3 标识或渐变底图） | 可选，属方案一变体 |
| `application/boot_splash/minimum_display_time` | ✅ | **非 macOS 平台是阻塞 `delay_usec`（`main.cpp:4877-4883`）** | **不推荐**：这是纯等待，直接延长启动，与"不增加耗时"的目标冲突 |
| `RenderingServer.frame_post_draw` | ✅ | 确认某帧已绘制 | **推荐**，用于精确定位"首帧之后" |
| `SceneTree.process_frame` | ✅ | 等一帧 | 可用，但不如 `frame_post_draw` 精确 |

### 2.3 由此推出的唯一可行路线

> **让主场景的第 1 帧"看起来就是 spl

ash 的延续"，然后从第 1 帧之后开始做动画。**

官方没有提供"从 splash 平滑过渡"的能力，但它提供了 `bg_color` 和"首帧内容由我决定"这两个自由度。方案二的本质就是把这两个自由度用到极致：首帧 = 与 splash 同色的全屏矩形（视觉上等于 splash 没有结束），随后淡出露出真实界面。

## 3. 三种方案对比

### 方案一：仅统一 Boot Splash 与正式背景的颜色

**做法**：把 `boot_splash/bg_color` 改成某个分区的底色（如 GAMES 的 `#0E1218`）。

| 维度 | 评价 |
|---|---|
| 消除割裂的效果 | 只消除第 1 层（色彩）。细节密度与运动的突变仍在 → 仍有"闪"的观感 |
| 分区兼容性 | **致命缺陷**：只能匹配一个分区。默认 `games` 尚可，用户若存的是 MOVIES/SYSTEM，色差反而更大（暖棕 vs 亮蓝） |
| 改动量 | 1 行配置 |
| 启动耗时 | 0 |
| 风险 | 极低 |
| 可撤销 | 改回一行即可 |

**结论**：可作为"配套微调"，不足以单独交付。

### 方案二：主场景内 CanvasLayer + Tween 淡入

**做法**：`_ready()` 末尾建一个全屏 `ColorRect`（颜色 = splash 底色），首帧以它呈现；`frame_post_draw` 后 Tween 把 alpha 1→0，结束即 `queue_free()`。

| 维度 | 评价 |
|---|---|
| 消除割裂的效果 | 三层一起解决：色彩由同色遮幕保证连续，细节与运动随 alpha 提升平滑浮现 |
| 分区兼容性 | **完全无关**：遮幕不关心底下是哪个分区 |
| 改动量 | `main.gd` 约 12 行（1 常量 + 1 函数 + 1 调用），`project.godot` 1 行配色 |
| 启动耗时 | 0（不阻塞构建，不等待） |
| 首帧 | 首帧内容从"完整 UI"变为"纯色遮幕"，即与 splash 无缝衔接 |
| 3D 渲染 | 不受影响（遮幕是 2D 层，3D 照常渲染，只是被盖住） |
| 窗口焦点 | 不受影响 |
| 性能 | 一个全屏矩形 alpha 混合，0.45 秒后销毁，可忽略 |
| 业务模块 | 零改动（不碰 section / theme / 3D / 网络） |
| 可撤销 | 删 3 处即回到现状 |

**风险点**：遮幕若用 `MOUSE_FILTER_STOP`，0.45 秒内的点击会被吞；用 `IGNORE` 则可能误点半透明的卡片。建议 `STOP`（0.45 秒的不可点比误触导航更轻）。

### 方案三：氛围光渐亮 + UI 分层显现

**做法**：把 `game_ambient` / `cinema_ambient` / `game_background` 的亮度/强度 uniform 从 0 渐升到现值，同时把 UI 分组用 modulate 分层淡入。

| 维度 | 评价 |
|---|---|
| 消除割裂的效果 | 理论上最好，可做出"灯光渐亮、界面逐层落位"的效果 |
| 分区兼容性 | **需要三套实现各写一遍**（ColorRect 着色器 / 两套 3D shader），且各分区参数不同 |
| 改动量 | 三个 shader 的 uniform 读写 + `game_section` / `movie_wall` / `main` 三处驱动 + UI 分组 modulate，估计 100 行以上 |
| 启动耗时 | 略增（首帧需要写入多组 uniform） |
| 3D 渲染 | **有实质风险**：与 `glow`、`ssao`、主题控制器、封面入场动画同时改同一批材质参数，容易出现"某次淡入后参数没恢复"的残留 |
| 业务模块 | 需要改动 section 模块内部，违反"不覆盖解耦成果"的精神 |
| 可撤销 | 差：散落在三处，漏删一处会长期影响运行时画面 |

**结论**：不推荐。收益（更好的观感）与风险（污染运行时状态）不成比例，且与"最简单、稳定、可撤销"的要求直接冲突。

### 对比总表

| 维度 | 方案一 配色 | 方案二 遮幕淡出 | 方案三 灯光/分层 |
|---|---|---|---|
| 消除色彩跳变 | ✅ | ✅ | ✅ |
| 消除细节突变 | ❌ | ✅ | ✅ |
| 消除运动突变 | ❌ | ✅（部分） | ✅ |
| 兼容三个分区 | ❌ | ✅ | ⚠️ 需三套实现 |
| 改动量 | 1 行 | ~13 行 | 100+ 行 |
| 触碰业务模块 | 否 | **否** | 是 |
| 可撤销性 | 极好 | 好 | 差 |
| 运行期副作用风险 | 无 | 无（对象 0.45 s 后销毁） | **有**（uniform 残留） |

## 5. 推荐方案（可直接实施的最小版本）

### 5.1 修改文件清单

| 文件 | 改动 | 规模 |
|---|---|---|
| `g3_frontend/project.godot` | `boot_splash/bg_color` → `Color(0.055, 0.070, 0.095, 1)`（= GAMES 底色 `#0E1218`） | 1 行 |
| `g3_frontend/scripts/main.gd` | 新增常量 `STARTUP_VEIL_COLOR`；新增 `_start_startup_veil()`；`_ready()` 末尾调用一次 | 约 13 行 |

**不修改**：`window_policy.gd`、`world_scene_builder.gd`、`game_section.gd`、`movie_wall.gd`、任何 `*.gdshader`、`runtime.py`、`run_windows.vbs`、WebSocket 协议、窗口初始尺寸。

### 5.2 实现要点（伪代码，供批准后落地）

```gdscript
# 与 project.godot 的 boot_splash/bg_color 必须完全一致
const STARTUP_VEIL_COLOR: Color = Color(0.055, 0.070, 0.095, 1.0)

func _start_startup_veil() -> void:
    # 首帧必须以纯色呈现，因此至少等一帧画完再开始淡出
    await RenderingServer.frame_post_draw

    var layer: CanvasLayer = CanvasLayer.new()
    layer.layer = 120                      # 高于分区遮幕(110)
    add_child(layer)

    var veil: ColorRect = ColorRect.new()
    veil.set_anchors_and_offsets_preset(Control.PRESET_FULL_RECT)
    veil.color = STARTUP_VEIL_COLOR
    veil.mouse_filter = Control.MOUSE_FILTER_STOP
    layer.add_child(veil)

    var tween: Tween = create_tween()
    tween.tween_property(veil, "color:a", 0.0, 0.45) \
        .set_trans(Tween.TRANS_SINE).set_ease(Tween.EASE_OUT)
    tween.tween_callback(layer.queue_free)
```

调用位置：`main.gd` 的 `_ready()` 末尾（`get_window().size_changed.connect(_on_window_resized)` 之后）加一行 `_start_startup_veil()`。

> 注：遮幕必须在 `frame_post_draw` **之后**创建，才能保证第 1 帧是纯色。若在 `_ready` 中同步创建，Tween 可能在同一帧就开始推进，导致首帧已经是半透明。

### 5.3 动画时间轴

| 时间 | 事件 | 屏幕表现 |
|---|---|---|
| T−（构建中） | `_ready()` 构建 3D/UI | Boot Splash 纯色（引擎绘制） |
| **T0（首帧）** | 遮幕以 alpha=1 覆盖全屏 | 仍是纯色，**与 splash 完全同色 → 无缝** |
| T0+0 ms | `frame_post_draw` 返回，创建 Tween | 纯色 |
| T0+0 → 450 ms | alpha 1 → 0，`SINE / EASE_OUT` | 界面由暗到亮浮现；封面入场动画同期进行 |
| T0+450 ms | `layer.queue_free()` | 完全等同现状 |

可选增强（不建议首次就加）：在淡出前插入 `tween.tween_interval(0.06)`，让纯色多停留 60 ms，避免"刚出现就开始亮"的仓促感。

### 5.4 验收标准

1. **首帧同色**：启动瞬间对窗口取样，首帧颜色与 `boot_splash/bg_color` 的 RGB 完全一致（可用截图取色，允许 ±2 的合成误差）。
2. **无整帧阶跃**：从窗口可见到淡出结束，连续采样同一像素点的亮度，**不存在单帧亮度跳变超过 8%**（当前实现的跳变是整帧级别的）。
3. **时长不增**：从窗口首次可见到可交互的总时长与修复前一致（±50 ms），因为遮幕不阻塞构建。
4. **三分区一致**：GAMES / MOVIES / SYSTEM 三个启动分区都能看到淡入，且都不出现色块。
5. **3D 与业务无回归**：SYSTEM 的氛围光波、MOVIES 的 cinema_ambient、GAMES 的封面入场动画照常播放；后端连接、窗口拖拽缩放、全屏切换不受影响。
6. **可撤销**：删除 `STARTUP_VEIL_COLOR`、`_start_startup_veil()`、调用行，并把 `bg_color` 改回 `Color(0.031, 0.067, 0.122, 1)`，画面行为与当前版本完全一致。

### 5.5 回滚方式

三处改动均为新增，回滚即删除：

```
project.godot        : bg_color 改回 Color(0.031, 0.067, 0.122, 1)
main.gd              : 删除 STARTUP_VEIL_COLOR 常量
main.gd              : 删除 _start_startup_veil() 整个函数
main.gd              : 删除 _ready() 末尾的 _start_startup_veil() 调用
```

## 6. 风险与边界

| # | 风险 | 等级 | 缓解 |
|---|---|---|---|
| R1 | 遮幕 `MOUSE_FILTER_STOP` 吞掉 0.45 s 内的点击 | 低 | 若不可接受，改 `IGNORE`；但会允许误点半透明卡片 |
| R2 | 遮幕颜色与 splash 不一致 → 出现"二次色差" | 低 | 两处使用同一常量，且注释互相指认 |
| R3 | 遮幕盖住了封面入场的开头 | 低 | 淡出 0.45 s 短于单张封面入场 1000 ms，仍能看到大部分入场过程 |
| R4 | 将来若 `_ready` 之后仍有异步内容（如封面异步解码），遮幕可能在内容未就绪时就淡出 | 中 | 淡出结束只代表"可见"，不代表"必须全部就绪"；当前封面入场本就在遮幕之后继续，属于既有表现 |
| R5 | 与 `_section_fade`（layer 110）层级冲突 | 极低 | 遮幕在 layer 120；且分区切换在启动瞬间不可能被触发 |

**明确不做（约束清单）**：不改窗口初始尺寸、不引入 1×1 透明窗口、不使用外部 Splash 或 NativeWindowGate、不做延迟 Reveal、不改启动器与 WebSocket 协议、不覆盖 `main.gd` 解耦成果。

## 8. 一句话总结

Boot Splash 无法被淡出，但**首帧长什么样由我们决定**。把首帧做成"和 splash 同色的全屏幕布"，再用 0.45 秒把它拉开——这是官方机制允许范围内，最简单、最稳、也最容易反悔的做法。
